# Getting help with Sange ecosystem projects

Different question types route to different surfaces. Picking the
right surface gets you a faster + better answer.

## Quick reference

| Question | Where to go |
|---|---|
| "How do I use X?" | [GitHub Discussions](https://github.com/orgs/sangedev/discussions) (per-repo or org-wide) |
| "I think this is a bug." | The product's own [Issues](https://github.com/sangedev/sange/issues) page |
| "I'd like to propose Y." | Discussions first, then a feature-request issue if the discussion lands on "yes, build it" |
| "I found a security vulnerability." | **NOT a public issue.** See [SECURITY.md](./SECURITY.md). Email [opensource@simtabi.com](mailto:opensource@simtabi.com). |
| "I want to commission custom work / consulting." | [imani@simtabi.com](mailto:imani@simtabi.com) — Imani Manyara, maintainer |
| "I want to sponsor / fund the project." | Funding mechanisms are TBD; reach out to `opensource@simtabi.com` for now |

## When you file an issue

Make us a kind reader:

- **Sange version** (`sange --version`) + OS + Python version.
- **Minimal reproduction** — the smallest case that triggers the bug.
  A failing test is gold.
- **What you expected** vs **what happened**. Stack traces if any.
- **What you've already tried**. Saves the reviewer from suggesting
  the same path you already explored.

The org's default issue templates capture all of this. Use them.

## When you ask in Discussions

Same idea, lower stakes — Discussions is for open-ended questions,
"is this the right approach for X?", "how do others solve Y?". You
don't need a repro case; you do need a clear question.

## Response times

| Channel | Target response time |
|---|---|
| Security vulnerability email | 48 hours (acknowledgement) |
| Security vulnerability email | 5 working days (initial assessment) |
| Issues (bug reports) | 5 working days |
| Discussions | best-effort; community-driven |
| Feature requests | best-effort; queued by alignment with the roadmap |

The maintainer is one person with a day job. We aim for these
targets but don't always hit them. Bumping a thread after a week
is reasonable; bumping daily is not.
