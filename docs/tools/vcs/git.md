# Git adapter

Sange wraps Git through a single `VCSDriver` Protocol; this doc
covers what Sange does on top of raw `git` — environment
discipline, structured output parsing, capability flags, and the
Sange-specific augmentations.

For the **exhaustive** Git command list (every Tier, every
Sange wrapper / AI augmentation / safety class / confirmation gate
column), see
[Appendix D — Git command catalog](../../reference/appendix-d-git-catalog.md).
The appendix is regenerated by T-G-001 from a live `git help -a`
and the Sange enrichment table.

## What Sange adds over raw git

| Raw git | What Sange adds |
| :--- | :--- |
| `git commit -m "..."` | Conventional Commits validation, AI-drafted messages via [`commits ai`](../workflow/commit-lifecycle.md#end-to-end-ai-flow), approval state, the 8-state lifecycle, durable JSON record under `.sange/commits/`. |
| `git push` | Force-with-lease as the safer default; `--porcelain` output parsing for stable no-op detection; per-ref state recording in the audit chain. |
| `git status` | Parsed into structured `StatusEntry` records (path / state / index_state / worktree_state) via `parse_status_porcelain_v2`. CLI surfaces use the structured form. |
| `git log` | ASCII-record-separator format (`\x1f` fields, `\x1e` records) so commit messages with tabs/newlines round-trip cleanly. |
| `git diff` | Stat parsing (`parse_shortstat`) + content hashing for audit-record correlation. |
| `git tag` | Annotated by default; signing pass-through (`--sign`) supported; deletion gated behind a confirmation prompt in `sange commit/release` flows. |

The raw `git` command always remains available — Sange never
hides or replaces git. The adapter is additive: every Sange verb
maps to one or more underlying git commands that you could run by
hand. Run with `--verbose` to see them.

## Environment discipline

Every subprocess call to `git` runs with a controlled environment.
The adapter is at `src/sange/adapters/vcs/git/_subprocess.py`:

| Env var | Value | Why |
| :--- | :--- | :--- |
| `LC_ALL` | `C` | Forces ASCII output. Locale-aware month names / number formats would break parsers across CI runners. |
| `LANG` | `C` | Same. |
| `GIT_PAGER` | `cat` | `git log` with a pager active hangs in non-TTY contexts. |
| `PAGER` | `cat` | Fallback for the `git config core.pager` lookup. |
| `GIT_TERMINAL_PROMPT` | `0` | Git can't prompt for credentials — fail fast instead of hanging on a missing TTY. |
| `GIT_OPTIONAL_LOCKS` | `0` (selectively) | Skips opportunistic `git gc` during read operations so a high-concurrency CI doesn't deadlock on lock files. |
| `PATH` | the system path | Inherits so the user's git binary is found. |
| `HOME` | the user's home | Required for `~/.gitconfig` to load — Sange respects user config. |

Sensitive credentials (e.g. `GH_TOKEN`, AWS keys) are **not**
forwarded into the subprocess unless explicitly declared in the
relevant flow (e.g. `sange commits push` doesn't need credentials;
`sange release publish` does, and asks for them by name).

Default subprocess timeout: 30 seconds per call. Long-running
operations override (e.g. `clone` of a large repo); the §7.0.6
streaming helper (deferred to v0.5+) is the path for ops that
don't fit a single buffered return.

## Capability flags

Git supports every optional sub-Protocol Sange defines, gated on
the installed version:

| Capability | Sange Protocol | Min git version |
| :--- | :--- | :--- |
| Stash | `SupportsStash` | 2.0 |
| Bisect | `SupportsBisect` | 1.5 (very old) |
| Rebase | `SupportsRebase` | 2.0 |
| LFS | `SupportsLFS` | git-lfs 2.0 alongside git 2.20 |
| Signed tags | (always) | 2.0 |
| History rewrite | `--force-with-lease` | 2.0 |

`GitDriver.capabilities` returns these flags at runtime by
parsing `git --version` once and caching the result. Sange
features that require a capability check it explicitly:

```python
caps = driver.capabilities(repo)
if not caps.supports_stash:
    raise UnsupportedOperation("This flow requires git stash")
```

In v0.1, every modern git (2.20+) satisfies the entire optional
set. The capability check is forward-looking: when Sange adds
adapters for VCSes that *don't* support stash (e.g. SVN), the
check stays correct without conditional code in the calling layer.

## The parser layer

Adapter output is parsed by pure functions (no subprocess, no
state). This means parsers are unit-testable without a git binary
installed — fuzz inputs, regression-test edge cases, run in
parallel.

| Parser | Reads | Returns |
| :--- | :--- | :--- |
| `parse_status_porcelain_v2` | `git status --porcelain=v2` | `tuple[StatusEntry, ...]` |
| `parse_log_records` | `git log --format=<asciirs>` | `tuple[LogRecord, ...]` |
| `parse_branch_list` | `git for-each-ref refs/heads/...` | `tuple[BranchInfo, ...]` |
| `parse_remotes` | `git remote -v` | `tuple[RemoteInfo, ...]` |
| `parse_tag_list` | `git tag -l --format=<asciirs>` | `tuple[TagInfo, ...]` |
| `parse_shortstat` | `git diff --shortstat` | `(files, insertions, deletions)` |
| `parse_version` | `git --version` | `Version` dataclass |

The ASCII record-separator design (`\x1f` between fields, `\x1e`
between records) handles commit messages containing tabs,
newlines, pipes, quotes, NUL bytes — anything except literal
ASCII RS / GS. Standard Unicode is safe.

## Push semantics

`GitDriver.push()` is the most-surprising surface for users coming
from raw git. Differences:

- **`force` and `force_with_lease` are mutually exclusive.** Pick
  one. Raw `git push --force --force-with-lease` quietly prefers
  `--force-with-lease`; Sange refuses the combination at the
  driver level so the caller is explicit about intent.
- **`--porcelain` is always passed** so per-ref outcome (`up-to-date`,
  `new`, `forced`, `rejected`) lands on stdout in a stable format
  the driver can parse into a `PushResult`. Raw git's default
  output is human-prose and changes across versions.
- **No-op pushes return** `PushResult(was_no_op=True)` rather than
  succeeding silently. Useful for CI scripts that need to
  distinguish "nothing to push" from "pushed N commits".
- **Branch override is optional.** When omitted, `GitDriver.push`
  runs `git push <remote>` and lets git's default-branch lookup
  resolve it. The test fixture in
  `tests/unit/test_cli_commits.py::_setup_git_repo` uses
  `git push -u origin main` once at setup to establish upstream
  tracking — newer git versions require this for subsequent bare
  `git push origin` to work.

## Commit semantics

`GitDriver.commit()` differences from raw `git commit`:

- **Author override is symmetric.** Passing `author_name` without
  `author_email` (or vice versa) is a `DriverError` rather than
  silently using the other value from `git config`. Both-or-neither.
- **`allow_empty` is explicit.** Defaults to `False`; raw git's
  default is also `False`, so semantics match — the explicit
  parameter makes the intent visible at the CLI level.
- **`sign` (passes `-S`) requires** a GPG configuration; the
  adapter doesn't try to configure GPG, just respects the flag.
  Missing-key errors surface as `DriverError("gpg: signing
  failed: ...")`.
- **Return value is a `CommitRef`** with sha + short_sha + the
  parsed author + the parsed message. The caller doesn't need
  to re-parse.

## Stash, bisect, rebase, LFS

These sub-Protocols are wired in v0.1 for capability detection;
the user-facing surfaces (`sange stash`, `sange bisect`, `sange
rebase`, `sange lfs`) land in v0.5+ per
[`../../governance/roadmap.md`](../../governance/roadmap.md).

The underlying adapter calls (`run_git(['stash', 'push', ...])`,
etc.) work today via `sange git` (the passthrough surface in §9.4)
— but the curated Sange wrapper with AI augmentation + confirmation
gates is v0.5+.

## Hooks and policy

Sange's hook engine (v0.5+) wraps `pre-commit`, `pre-push`, and
`pre-merge-commit` git hooks. The contract: any executable in
`.sange/hooks/<name>/<priority>-<slug>` runs in priority order;
any exit code other than 0 fails the gate. The library ships
named gates for `gitleaks` / `trufflehog` / `make test` /
`make lint` / `mypy` / `ruff`.

Hooks are stored under `.sange/hooks/` rather than `.git/hooks/`
so they're committable as part of the repo. The `sange init`
command writes the shim into `.git/hooks/<name>` that defers to
`.sange/hooks/<name>/`.

## Common pitfalls

- **CI runs different git versions than your local.** This bites
  generators that introspect `git --version` (T-G-001 in
  particular). Sange handles this by skipping T-G-001 + T-G-002
  from the CI `all.py --check` run; contributors regenerate
  locally when they consciously refresh the catalog. See
  [`../../release.md::Step 0`](../../release.md#step-0--pre-flight-checklist).
- **Newer git requires `-u` for first push.** The
  `push.autoSetupRemote` config flag flips this default, but CI
  runners don't set it. Set upstream once with `git push -u
  origin main` before relying on bare `git push origin`.
- **Locale-bearing git outputs.** Sange's `LC_ALL=C` discipline
  ensures parser stability; if you bypass the adapter and call
  `subprocess.run(['git', ...])` directly without env discipline,
  the parsers may not survive non-en_US locales.
- **`.gitconfig` includes.** Sange respects `~/.gitconfig` via
  `HOME=...` in the env; if your `.gitconfig` includes a malformed
  file, git itself errors out before Sange sees anything. `git
  config --list` is the diagnostic.
