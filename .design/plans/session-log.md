# Session log

> Append-only diary of every working session on this project. Updated by the responding model **after every task completion**, not at session-end. The log is the audit trail an auditor (or a future session) reads to know what changed when, by whom, and why.

## Method — when and how to append

A new entry is appended:

1. **After every `TaskUpdate` flips a task to `completed`** in the harness task list.
2. **After every accepted ADR** (cross-reference the ADR number in the entry).
3. **After every closed risk** (cross-reference the R-NNN id).
4. **After every meaningful file create / move / delete** that affects the design surface (the prompt, the deliverable, or any `plans/` file).
5. **After every clarifying-question / answer exchange with the user** where the answer became a decision (ADR or §-anchor edit).

The entry shape is fixed. Use the template at the bottom. The columns are mandatory; freeform notes go in the bullets below the table row.

## Method — what an entry contains

| Field | Rule |
|---|---|
| `id` | `S-NNN-T-MM` — session number, task number within session (e.g. `S-001-T-04`). Monotonic. Durable across sessions. |
| `timestamp` | ISO-8601 UTC. The time the *task completed*, not when the entry was appended. |
| `actor` | `user@host` of the operator; for AI-driven entries, `model:claude-opus-4-7@user@host` (the responding model + user). |
| `surface` | The surface where the work happened: `prompt`, `architecture`, `plans`, `code`, `kit`, `audit`. |
| `action` | One-line imperative verb-phrase. "Added §43 Testing Strategy" — not "I added §43". |
| `files_touched` | List of files (relative to the repo root) the action created / modified / deleted. |
| `grounding` | (added in v4.4 per ADR-030) List of files the model READ before performing the action — the basis for any factual claims in the action. Proves anti-hallucination compliance. Empty only for trivial actions like "ran `wc -l`". |
| `linked` | ADR-NNN refs, R-NNN risk refs, T-NNN checklist refs, S-NNN session refs, prompt §-anchors. |
| `audit_chain` | (Optional) The `entry_hash` from the global `.sange/audit/` log entry that mirrors this session-log row, when the project is far enough along that the runtime audit chain is producing entries. |
| `notes` | Freeform bullets — *why*, edge cases, follow-ups discovered. Use `🟡 UNVERIFIED`, `✅ Verified`, `❌ Refuted` markers per ADR-030. |

## Method — audit after every step

The session-log row **is** the audit step. There is no separate "audit-after-task" step beyond appending this row. The integrity comes from:

- The log being append-only (no edits to prior rows; corrections go in a new row referencing the prior `id`).
- The `linked` column tying every entry to a verifiable artifact elsewhere (ADR row, risk-register row, prompt §-anchor, checklist task, git commit hash when applicable).
- The `audit_chain` column (when present) linking the design-time row to the runtime `.sange/audit/` JSONL chain, so the same operator's design decisions and runtime actions are correlated.

Once the v0.1 code is up and the daemon is producing real audit JSONL, the session-log can be emitted automatically from those entries via `tools/generators/session_log.py` (a future T-G generator) — until then, manual append is the rule.

## Method — checklist integration

When a session-log entry corresponds to a `checklist.md` task completion, the entry's `linked` column **must** name the task ID (e.g. `T-001`, `T-G-005`). The reverse pointer — from `checklist.md` to the session-log row that closed it — is added by editing the task description with `(closed in S-NNN-T-MM)`. This makes the checklist's history machine-readable.

When a task is partially complete (real work happened but acceptance criteria not yet green), a session-log entry **may** still be appended with `action: progress` and `linked: T-NNN (in-progress)`. The checklist task stays unchecked.

## Method — fork-friendliness (per ADR-025 godmode workbook)

This file's *structure* is reusable for any future agency project. The Sange-specific entries below get truncated/deleted when forking; the **method** sections above stay. Future projects copy the template, increment session numbers from `S-001-T-01`, and rely on the same audit shape.
